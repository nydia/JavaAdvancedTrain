# Redisson延迟队列底层原理解析

## 一、Redisson延迟队列简介

Redisson是基于Redis实现的分布式延迟队列，专为延迟执行的业务任务设计，是分布式系统中处理延时任务的轻量方案，核心适用场景如下：

- 订单超时未支付自动关闭

- 预约/签到任务到期提醒

- 业务超时自动取消、资源解锁

- 分布式场景下的延时调度任务

该延迟队列具备轻量易用、天然分布式、支持任务取消、依托Redis持久化保证数据不丢失等核心特点。

---

## 二、核心底层数据结构

Redisson延迟队列并非单一Redis结构，而是由**两个Redis核心结构+一个客户端后台线程**配合实现，各司其职：

1. **ZSet（有序集合）**

    - 用于存储**未到期**的延迟任务

    - value：存放任务具体内容，通常为业务唯一标识（如订单号、任务ID）

    - score：绑定任务的到期时间戳，用于排序和判断是否到期

2. **BlockingQueue（List结构）**

    - 用于存储**已到期**的任务

    - 供消费者阻塞式获取并执行业务逻辑

3. **客户端后台轮询线程**

    - Redisson客户端启动后，内置守护线程持续定时运行

    - 定时扫描ZSet中的任务，筛选出已到期任务

    - 将到期任务从ZSet转移至阻塞队列，等待消费

## 三、整体执行流程

```Plain Text
添加延迟任务
    ↓
存入Redis ZSet（score=任务到期时间戳）
    ↓
后台线程定时扫描ZSet集合
    ↓
判断任务是否到期（score ≤ 当前时间戳）
    ↓
到期任务：从ZSet删除 → 移入阻塞队列List
    ↓
消费者通过take()方法阻塞获取并消费
```

## 四、详细执行原理

### 1. 添加延迟任务

调用延迟队列添加任务的API：

```Java
delayedQueue.offer("order_1001", 10, TimeUnit.SECONDS);
```

底层执行步骤：

1. 计算任务到期时间戳：当前系统时间 + 设置的延迟时长

2. 执行Redis命令，将任务存入ZSet：
   `ZADD {delayQueueKey} {timestamp} {taskId}`

### 2. 后台线程轮询

Redisson内置守护线程持续循环，定时执行Redis命令，扫描到期任务：

```Plain Text
ZRANGEBYSCORE {delayQueueKey} 0 {now} LIMIT 0 1
```

检测到任务到期后，执行两步原子操作：

```Plain Text
ZREM      {delayQueueKey} {taskId}
RPUSH     {blockingQueueKey} {taskId}
```

### 3. 消费者消费任务

消费者通过阻塞方法获取到期任务：

```Java
blockingQueue.take();
```

底层对应Redis阻塞命令：

```Plain Text
BRPOP {blockingQueueKey} 0
```

- 队列无消息时：线程阻塞等待，不占用CPU资源

- 队列有消息时：立即获取任务，并从List中移除

## 六、选用ZSet的核心原因

1. 按score自动排序，可快速定位最早到期的任务，提升扫描效率

2. Redis单线程执行命令，天然保证分布式场景下不重复消费

3. 支持通过ZREM快速删除任务，完美实现取消延迟任务的需求

4. 内存存储结构高效，可承载大量延迟任务，性能优异

## 七、优点与缺点

### 优点

- 接入简单，轻量无重量级中间件依赖，部署成本低

- 天然支持分布式，多服务实例部署不会出现任务重复执行

- 支持随时取消延迟任务，使用灵活

- 开启Redis持久化后，服务重启、Redis重启任务不丢失

### 缺点

- 时间精度有限，默认约100ms误差，依赖后台轮询间隔

- 无内置ACK确认机制，消费异常可能导致任务丢失

- 不支持消息重试、死信队列等高级消息特性

- 强依赖Redis可用性，Redis故障会导致延迟队列不可用

## 八、生产常见问题

### 1. Redis重启，任务会丢失吗？

- 开启RDB + AOF持久化：**任务不丢失**，重启后自动加载

- 未开启持久化：**任务全部丢失**，内存数据清空

### 2. Java服务重启，任务会丢失吗？

**不会**，任务存储在Redis中，与Java服务生命周期无关，重启后重新连接即可继续监听。

### 3. 为何会出现RedissonShutdownException？

服务关闭时，Spring容器先销毁RedissonClient客户端，而延迟队列监听线程仍在执行take()阻塞操作，操作已关闭的客户端，从而抛出该异常。

解决方案：通过@PreDestroy实现优雅关闭，中断监听线程，再销毁客户端。

### 4. 如何保证任务不丢失？

- Redis开启RDB+AOF持久化

- 任务落地数据库，标记任务状态

- 消费异常增加重试机制

- 消费完成后更新任务状态，做幂等处理

## 十、核心原理总结

Redisson延迟队列基于**Redis ZSet有序集合**实现，将任务到期时间戳作为score排序，通过客户端后台线程定时扫描ZSet，筛选出到期任务并转移至阻塞队列，最终由消费者通过BRPOP命令阻塞消费，是轻量分布式延时任务的优选方案。
